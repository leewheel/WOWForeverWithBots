# Module System — Phase 4 Design: Capability Approval & Audit Logging

Status: design drafted, not yet implemented.
Builds on `00-investigation.md`, `02-phase0-decisions.md`, `01-first-steps-plan.md`, `03-phase1-protocol-design.md`, `04-phase2-module-host-design.md`, `05-phase3-build-discovery-design.md`.

Goal: since Tier 1/Tier 2 APIs are the only real enforcement boundary (declared capabilities aren't otherwise sandboxed), give operators visibility **and** a deliberate gate whenever a module's declared capabilities change — so a module update can't silently escalate what it asks for.

## 1. Capability hash & approval store

- New file `approved_modules.json` (location: core's config directory, **not** `Modules.Dir`/`modules_runtime` — that directory gets regenerated by the Phase 3 build step, approval state must survive rebuilds).
- Structure:
  ```json
  {
    "hello-module": {
      "capability_hash": "<sha256>",
      "approved_version": "0.1.0",
      "approved_at": "2026-10-12T14:00:00Z"
    }
  }
  ```
- `capability_hash` = SHA-256 of a canonicalized JSON object containing **only** the capability-relevant fields: sorted `tier1.hooks` array + the full `tier2` block (`participates`, `requested_max_bots`, `requested_max_nearby_units`, `requested_max_actions`, `requested_tick_interval`). Deliberately **excludes** `name`/`version`/`sdk_version` — a module bumping its version or fixing a bug shouldn't force re-approval; only an actual capability change should.

## 2. Load-time gate (in `ModuleMgr::LoadModules()`, before spawning)

For each discovered module:

1. Parse `module.json`, compute `capability_hash`.
2. Look up `approved_modules.json` by module name:
   - **No entry (never seen before)**: do **not** spawn. Log clearly (see §4) what it's requesting and the exact command to approve it. Status = `pending_approval` (a third status alongside Phase 2's `permanently_failed`/`transient_failed`/`running` — distinct because it's an operator action pending, not an error).
   - **Entry exists, hash differs**: do **not** spawn. Log a diff of old vs. new declared capabilities (added/removed hooks, Tier 2 newly enabled/disabled, bounds increased). Status = `pending_approval`.
   - **Entry exists, hash matches**: proceed to spawn normally (Phase 2 flow). Log at info level.
3. **Dev-convenience override**: `Modules.AutoApproveLocal` config flag (default `0`). When `1`, skip the gate entirely and auto-approve on every load — intended for local dev iteration (rebuilding/testing your own modules constantly), explicitly documented in `worldserver.conf.dist` as **not for production use**.

## 3. Operator approval action

- New worldserver **console command** (not an in-game GM command — this is a server-operator/config-level action): `module approve <name>`.
  - Recomputes current `capability_hash` from the module's current `module.json` on disk, writes/updates the `approved_modules.json` entry, logs the approval with timestamp.
  - v1 scope: takes effect on the **next module load pass** (server restart, or a future manual rescan command) — not a live "spawn immediately without restart" path, to avoid intertwining approval with the startup-only `LoadModules()` flow. Live-reload of newly-approved modules without restart is a reasonable later enhancement, not required for v1.
- Companion introspection commands: `module list` (name, status, version, approval state), `module info <name>` (full declared capabilities, Tier 2 bound usage if running, heartbeat/last-seen, restart count).

## 4. Audit logging

- New dedicated logger channel `modules` (TrinityCore's existing named-logger-channel convention, configured in `Logs.conf`/`worldserver.conf` the same way other subsystems already do) — keeps module lifecycle noise separable from general server logs.
- Events logged through this channel:
  - Discovery: module found, manifest parsed, capability hash computed.
  - Pending approval: full declared-capability summary + exact `module approve <name>` command to run.
  - Capability diff on change: explicit before/after list.
  - Approval granted (via console command).
  - Handshake: version check result, accept/reject + reason.
  - Spawn/restart/crash/permanent-failure (ties into Phase 2 §5 restart policy).
  - Bot control: `ControlRequest` granted/denied, `ReleaseControl`, `ControlRevoked` (ties into Phase 2 §6) — audit trail of which module controls which bot GUIDs over time.

## Deferred from this phase

- Live re-scan/hot-reload of `Modules.Dir` without a full restart (would let `module approve` take effect immediately) — nice-to-have, not required for a working v1.
- Any community-facing module registry/review/signing layer (mentioned as a social/operational trust layer in the original trust-boundary discussion) — out of scope for this core-repo work entirely; would live in a separate project/website, not this codebase.
